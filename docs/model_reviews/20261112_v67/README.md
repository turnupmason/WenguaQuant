## 为什么停，修了什么

正式训练的56个train显存样点无OOM计数、无free0；最低空闲6.746GiB、峰值reserved7.910GiB。停止发生在独立的第一轮**评估进程**，不是训练超出显存后丢失226步。

失败回执是`AcceleratorError: CUDA error: out of memory`。旧识别器没有将这种异步报错标为`cuda_oom=true`。旧评估路径没有逐答缓存清理，心跳和显存记录也只留下加载前一条：开始空闲14.72GiB。因此能确认评估OOM，**不能确认缓存增长是唯一原因，也不能排除当时其他GPU占用**；没有保存故障栈和OOM瞬间显存，不能事后编造具体算子或额外占用数。

新恢复模块放在`wengua_recovery/v67_evaluation.py`，329冻结项、原课程、训练器与原权重不改。只允许对已经完成两轮训练的原run做推理：

1. 校验原来源、软件版本、训练状态、全部问题/预算和既有答案前缀；父161答与第一轮124答的原字节固定，只可追加。
2. 使用原canonical `one_answer`，相同精度、模型、seed、上下文、512token预算及实际自身历史；不缩短问题、不更换教师、不插正确历史。
3. 每答结束清理空闲CUDA缓存并记录前后显存；每进程最多24个新答后退出。新的进程从已保存的真实先前回答恢复多轮历史。
4. 识别异步CUDA OOM，有限地换新进程重试；同一位置最多两次尝试，仍失败就保留记录停止，避免无限循环。
5. 补第一轮剩余37答，再评第二轮161答，总共198；不调用任何训练接口，新增训练更新数为0。完成后才将整体状态标为待审阅。

真实微型Qwen/PEFT CPU检查已经注入原评估OOM，再跨进程补答；核对了所有训练adapter、检查点和原答前缀字节未变，多轮确用模型实际先前回答，完成后再启动不增加worker。Windows原生CMD和Linux流程通过实际Actions核对。软件检查不能冒充这台4080上的修复效果或模型专业提升；本机补评估后再看完整记录。
